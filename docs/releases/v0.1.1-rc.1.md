# Yosh v0.1.1-rc.1

产品版本：**Yosh 0.1.1**。候选标识：**0.1.1-rc.1**。原生构建编号：**2**。

本候选完成 Yosh × Pay MCP 的版本与交付工程整合，保留已经审查的五项正确性修复。它不扩展钱包、签名、资金授权或受控请求范围，也不代表已经完成安装版、真实宿主或 Mainnet 资金验收。

这些输入包含未提交的 overlay，不能用单一 Git SHA 表示完整候选。随候选输出保存的源码清单及 Build Provenance Manifest 才是本次构建的完整身份：它们记录实际 revision、增量指纹、输入文件、构建参数及产物 SHA-256。Pay 和 pay-kit 保留各自版本号。

当前集成仍使用固定的 Pay / pay-kit fork 与尚未作为正式上游发行依赖交付的扩展接口；不得将本地可构建候选称为已合并或已发布的上游能力。PR 状态说明属于候选依赖边界，不是本轮对远端 PR 状态的实时查询。pay-kit #393 继续独立维护，本轮不修改、合并或重发该 PR。

唯一 RC 构建入口是 `scripts/build-release-candidate.py`。按该入口的命令帮助冻结、检查与构建；历史 Dev / staging 脚本保留原用途，不作为本版本的 RC 来源证明。RC 流程从核对后的输入构建 Native App、Backend、Pay MCP 与 Protocol Engine，并拒绝来源不匹配的旧产物。

在独立 Yosh 工作区中执行（`../pay` 与 `../cargo-home` 为已核对的候选源码和离线依赖缓存）：

```sh
python3 scripts/build-release-candidate.py freeze
python3 scripts/build-release-candidate.py check
python3 scripts/build-release-candidate.py build \
  --node-archive /absolute/path/node-v24.21.0-darwin-arm64.tar.xz
python3 scripts/build-release-candidate.py verify
```

`freeze` 记录所有已跟踪源码、未提交 patch 和非 ignored 新文件；冻结后修改源码会使构建失败。输出默认为 `build.noindex/release/v0.1.1-rc.1/`，已有输出目录会被拒绝覆盖。失败运行保留日志；重新构建使用新的 `--output` 目录。完整源码归档、`source-lock.json`、依赖文件指纹、命令日志、`build-provenance.json`、签名后的 `bundle-files.json` 和最终 `candidate.json` 一并保留。

Node 24.21.0 官方归档必须匹配脚本锁定的 SHA-256。当前流程显式复用本地 `node_modules` 与 Cargo 离线依赖缓存：逐包检查 npm 锁定版本，记录实际依赖文件指纹，记录 Cargo vendor / source replacement 配置，并在构建结束再次核对。它不声称执行过全新 `npm ci`。应用组件从空 Rust target、独立 Xcode DerivedData 和当前 Backend 源码重新构建。构建及测试子进程禁止外部网络，仅模拟服务相关阶段开放 loopback；真实钱包、生产数据与 Keychain 不属于输入。

输出 App 名称为 **Yosh Pay Dev v0.1.1-rc.1.app**，位于单独候选目录。构建不会安装、启动或覆盖已有 Yosh Pay Dev.app / Yosh.app，也不会写入 Codex MCP 配置。安装和人工验收需要后续独立决定。

## 能力边界

| 范围 | 当前候选的能力与限制 |
| --- | --- |
| Yosh 经济权限 | 后端维护 Agent / CardMember、资源范围、Spend Grant、共享 Daily Budget、原子预占、购买幂等和持久 Ledger。付款、交付与恢复分别建模；App 负责展示和管理输入。 |
| Pay MCP 接入 | Pay 识别 x402 challenge、选择报价并通过 pay-kit 准备未签名交易。SpendingAuthority 将经济事实交给 Yosh，ControlledExecution 委托 Yosh 完成受控执行及原购买恢复。 |
| 当前受控 GET Profile | 仅支持当前实现的 Solana USDC exact 路径；请求必须是 GET、无 body，只接受当前合同允许的 `accept: application/json` 请求头。Mainnet 请求还必须匹配已注册资源与现有授权条件。 |
| 交付 | HTTP 资源响应受 262,144 字节策略上限约束；最大 JSON 序列化结果为 1,572,866 字节。通用 delivery 以 16 KiB 分块读取，MCP continuation 使用同一上限；Pay 大结果使用其已有结果文件机制。 |
| 观察数据 | Activity / Trace 展示购买及调用路径事实；Trace 不替代 Ledger 中的付款或交付结论。 |

Yosh 通用 Resource 模型中已有声明式 query / JSON body、POST 审阅和授权相关代码及测试。**这不表示 Pay MCP 受控路径已经支持 POST 或完整通用资源生命周期。** Pay POST、任意请求头/body、任意网络/资产/scheme、所有商家兼容性和完整安装版生命周期不属于本 RC 的已验收能力。不得通过扩展 Profile 来完成本轮交付。

Pay 普通 replay 仍要求取得并匹配原 challenge。商家离线或改变 metadata / alternatives 时，原结果不一定能通过该调用透明取回；本 RC 不新增读取或恢复入口。

## Offline Dev 与 Mainnet

- **Offline Dev** 使用本地模拟商家、模拟链响应、临时测试身份及独立数据目录。测试结果证明本地集成行为，不证明真实网络、资金或 Mainnet 验收。
- **Mainnet** 保留现有独立环境、资源匹配、配置与授权条件；候选构建本身不会开启生产执行，也不授予付款许可。Mainnet 需要单独的明确授权和后续安装验收；本轮不执行真实付款。
- 生产钱包、正式 Ledger、Keychain 和现有 Codex 配置不是 RC 构建输入，不复制进候选包。

## 验证与验收

普通 `npm test` 不应依赖相邻 Pay checkout、Rust binary 或历史源码；完整 Pay 测试继续通过显式 `npm run test:pay` 在隔离环境运行。默认测试发现机制必须覆盖新增环境依赖 suite，防止联合测试再次漏分流。

本候选的实际通过数量和构建结果以随输出保存的本轮验证记录为准。构建成功及离线回归通过不等于 App 已安装、实际 Codex 宿主已接入或真实 Mainnet 付款已验收。历史成功记录仅保留历史含义。

本轮交付止于候选包完整性、版本和来源校验，之后等待安装及人工验收决定。
