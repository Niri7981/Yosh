# 真实内部函数调用链（本轮代码）

进程事实：普通集成测试中，SDK 客户端、Yosh AppRuntime/Adapter、假商家及假 RPC 都在同一个 Vitest Node 进程；真实 PayMcp 在独立 Rust 子进程。SIGKILL 用例将 Yosh Runtime/Bridge 放入独立 Node worker，商家/RPC 留在父进程。协议观察 helper 是另一个 Rust 子进程。**本轮没有交付或验收产品态独立 Yosh daemon / 已安装 Codex → Pay 注册链路。** 下列“Yosh”指业务代码执行位置，不自动表示单独进程。

1. **Agent 发起真实 MCP。** `tests/helpers/pay-production-fixture.ts::connectPay / callPay` 用 MCP SDK `StdioClientTransport` 启动真实 Pay Rust binary，执行 `client.callTool({name:'curl', arguments:{operation_id,url}})`。只提供 HTTP 请求与稳定 operation；不提供授权布尔值、私钥或交易。
2. **Pay 解析宿主上下文。** `../pay/rust/crates/mcp/src/server.rs::PayMcp::curl` 调用 `PayContext::scope / spending_authority`。当前测试实现位于 `src/bin/yosh-controlled-mcp.rs::Bridge`：配置由测试宿主写入，包含 backend-issued Connection token 与预期 caller。它不是已完成的产品凭据发行通道；Agent clientInfo 不建立身份。
3. **冻结请求/连接内防重。** Pay `src/tools/curl.rs::run` 规范化 HTTP method、headers/body，调用 `authority.rs::Operations::start` 绑定 caller + operation 并生成 attempt UUID。请求携带现成支付/认证头、缺少 operation、冲突或连接内重复会被拒绝。该 Map 不是持久账本。
4. **Pay 原 HTTP/402 编排。** `curl.rs::do_paid_fetch` 的原 fetch closure 调用 `pay_core::client::fetch::fetch_request_with_body_for_policy`，再经 `raw_to_outcome` / `runner::classify_402` / 原 SDK selector 得到 `RunOutcome::X402Challenge`。既有 YAML permission 检查仍独立执行；受控模式禁止重定向与不支持 flow，不另写简化 runner。
5. **Pay External Authority。** `authority.rs::AuthorityAttempt::authorize` 从实际 selected offer 构造 `SpendRequest`：caller、operation、attempt、不可变请求、atomic amount、asset、network、recipient、完整 accepted。`SpendingAuthority::authorize` 在限时内调用测试 Bridge `/pay/authorize`；Deny、超时或故障不进入 unsigned/sign/send。
6. **Yosh 认证并授权。** fixture 的 `/pay/*` handler 每次先执行 `AppRuntime::authenticateAgent(request,'request_purchase')`，得到真实 CardMember/Connection principal；随后 `pay-authority-adapter.ts::authorize / parse` 要求 caller 一致并校验选定报价与 Resource。`AppRuntime::runExternalPaymentOperation` 将工作纳入退出等待。`request-paid-resource-purchase.ts::requestPaidResourcePurchase({deferExecution:true, externalExecution:...})` 使用 Pay 已选择的不可变报价，复用 `PurchaseLedger::spendAuthorityForDecision / reserve`，执行真实 Grant、Daily Authority、预算判断。
7. **同事务 reserve 与 provenance。** `PurchaseLedger::reserve` 在 `BEGIN IMMEDIATE` 中保存唯一购买、预占与 `ExecutionSafety::reserve` 的来源/attempt/facts/quote/owner/epoch。没有第二个金额账本。`ExecutionSafety::enable / open` 负责 migration、writer lock、持久 owner/epoch 与 SQL writer guards。来源缺失的历史行不会被当作外部授权。并发 winner 的 permit 只能返回给原 attempt。
8. **Pay 取得公开准备参数。** 原 exact 分支在 Authority Allow 后调用 `controlled.rs::run` → `Bridge::plan` → Yosh Adapter `plan/get`。Yosh 核对持久 permit、当前 owner/epoch、facts/attempt，返回 public payer 和显式 RPC；已完成购买可返回只读 Replay。未决原 operation 不创建新付款。
9. **Pay 构造 unsigned。** `controlled.rs::prepare` 经有界 RPC 取得 blockhash/height，调用真实 `pay_kit::x402::client::exact::prepare_unsigned_payment`。实现位于 `../pay-kit-current/src/x402/client/exact/payment.rs`，与原 `build_payment` 共用构造代码。返回全零 signature slots 的 wire + lifetime；当前受控 prepare profile 仍只准入 loopback RPC。Pay 没有买方签名器。
10. **Yosh 取得唯一执行权。** `Bridge::execute` 将 facts + unsigned 发送 `/pay/execute`。Yosh Adapter `execute` 再次认证/绑定，私有 map 按 approval 保存本次 unsigned，调用 `approved-payment.ts::executeApprovedPayment(..., executor, permit)`。`PurchaseLedger::claim` 原子检查 Grant/Budget/Pause、来源及 permit，阶段推进 CLAIMED；默认 JS claim 缺少外部 permit 时不能领取这笔付款。
11. **Yosh 严格检查并签名。** `isolated-pay-execution.ts::prepare` 从 Adapter `takeUnsigned` 取得 wire，检查零签名、blockhash、`original-payment-evidence.ts::assertUnsignedPaymentBindings` 的指令/账户/币种/金额/收款方/fee payer/memo，并模拟交易。`context.beforeSign` 调用 `PurchaseLedger::assertCanSign(...,permit)`，复核持久 epoch 与实时经济权限，之后才调用 Yosh 持有的 signer。测试用离线内存 signer；生产 Keychain 通道本轮未启用。
12. **原证据、最后 gate 与提交 marker。** `executeApprovedPayment` 构造 `originalEvidence`，`PurchaseLedger::savePayload` 同事务保存买方签名 payload、不可变 `OriginalPaymentRecord` 与 SIGNED 阶段。之后 executor `assertBeforeSubmission`、`PurchaseLedger::markSubmissionAttempt(...,permit)` 复核原执行代次并保存 SUBMISSION_ATTEMPTED / 原时间戳。
13. **最终 HTTP 是 Yosh 发出。** `executeApprovedPayment` 在 marker 之后立即调用已准备的 `submit()`（HTTPS 使用 `prepareSafeResourceFetch`，本轮为 loopback fetch），携带原 `PAYMENT-SIGNATURE`。marker 与首次调用之间没有 await；凭据不交给 Pay 发送。已开始 HTTP 的原付款仍核对，不因 Pause 再生成付款。
14. **Yosh 独立核对并保存 API 数据。** 商家 response 先经 `readSettlementTransactionHint / observeTransactionSignature / observeDeliveryReceipt`；receipt 只是观察。`reconcileApprovedPayment` → `reconcileStoredOriginalPayment` 使用原 message/signature 与 RPC 原交易证明，`confirmOriginalPayment` 一次记账。只有 PAID 后 `receiveOriginalDelivery` → `consumeDelivery` 校验并持久保存 Resource 数据。原响应及可能反射的付款证据留在 Yosh。
15. **Pay 解释并返回 Agent。** Yosh 仅在原付款证明及持久交付成立后返回 credential-free 状态/JSON 数据；直接签名反射被拒绝。协议观察 helper 的 `interpretResponse` 只得到脱敏 receipt，不作经济判断。Pay `controlled::run` 将结果交给原 `fetch::raw_to_outcome → curl::interpret_retry → PaidFetchResult::into_tool_result`，经真实 MCP 返回 API 数据。解释失败不会抹掉已经确认的付款和数据。
16. **失败、Unknown 与重启。** 提交前能证明未发送的失败由 `failUnsubmitted` 处理；marker 已存在、HTTP/ACK 丢失或链上不明时保留原 payload、预占与 Unknown。新 AppRuntime 持有独占目录/ledger writer 后接管并递增 epoch；`recoverOnStartup → recoverUnsubmittedOnStartup / reconciliation.recoverClaimsOnStartup / recoverApprovedPayment` 只核对原付款，必要时经 `recoverPaidDelivery` 使用原凭据恢复交付。旧 permit 不能复活；相同 operation 不再签名。真实 SIGKILL 已覆盖 marker 前、marker 后 HTTP 前、商家收到 HTTP 后。

仍需人工 Review 的反例：旧 `b544227` 的 `approved-payment.ts::recoverApprovedPayment → receivePayment` 会在写账之前发送 `fetch`。冷启动拒写不是可靠的旧凭据出网隔离；实际旧暖进程反例已保留。故当前可审阅代码与证据，不能进入产品 staging 或生产验收。
